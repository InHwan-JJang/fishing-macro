## 2026-10-28 추가 버그 수정

사용자 스크린샷 3건을 바탕으로 `fishing_history.py`를 수정했습니다.

- 어비스 37.4m와 거북선 246.7m: 기존 정규식이 cm만 인식하여 이름·크기가 누락됐습니다.
  m도 인식하고 저장·표시 단위인 cm로 환산합니다.
- 동시 응답: 기존 단일 active 응답에 후속 카드를 계속 합치던 구조를 응답별 컨텍스트로 바꿨습니다.
  같은 종류의 미완료 응답에 카드를 순서대로 연결하며 친구의 컨텍스트도 유지합니다.
- 친구의 진주 + 내 복어: 진주 카드는 진주 응답에, 물고기 카드는 물고기 응답에 연결해
  복어 기록에 진주가 합산되는 문제를 방지합니다. 카드 종류가 다르면 도착 순서가 바뀌어도 분리합니다.
- 친구의 보정 어종 카드 때문에 내 미끼 사용이 예약되지 않는 것도 테스트했습니다.

추가 회귀 테스트 포함 **32개 통과**. 이번 검증은 이미지 문구를 바탕으로 구성한 테스트이며
문제가 발생한 당시 전체 복사 원문을 재생하거나 실제 동시 응답을 다시 발생시킨 검증은 아닙니다.
기존 저장 JSON은 수정하지 않았습니다. 과거 잘못된 기록 복구에는 해당 구간 원문 대조가 필요합니다.
명령/응답 헤더의 FIFO 대응은 유지하며, 같은 종류 카드의 역순·누락까지 완전히 해결한 것은 아닙니다.

## 사용자와 합의한 전제

- 전체 선택·복사로 대화를 읽고 기존 텍스트 클립보드를 복원하는 방식을 유지합니다.
- 명령/답장의 순서 기반 연결과 답장 누락 시 계속 낚시하는 동작을 허용합니다.
- 시작 전 횟수 조회를 추가하지 않습니다. 첫 낚시 답장으로 오늘 횟수와 한도를 확인합니다.
- 채팅방 선택과 멘션 대상 선택을 일반화할 필요는 없습니다.
- 자동어는 `수동` 명령 해제를 전제로 하며 실패 상황 보강은 사용자 우선 요구가 아닙니다.
- 미끼 최대 사용량은 최종 지시 기준 **하프물범 10개, 만년화리 20개**입니다.
- 예약 시각의 “오전 12시”는 한국 시간 **00:00:05**로 구현했습니다.

## 중요한 장애와 해결

초기 새 버전에서 오늘 횟수와 히스토리가 모두 갱신되지 않았습니다.
짧은 복사 예시 테스트만으로는 발견하지 못했고 실제 카카오톡에서 재현했습니다.

- 전체 복사 내용은 약 526만~530만 자, 약 65,000개 메시지 규모였습니다.
- 텍스트 파서 자체는 해당 대화를 해석할 수 있었습니다.
- 실제 매크로는 포커스/키 입력 성공인데도 매번 `chars=None`으로 기록됐습니다.
- 대기 중 클립보드 시퀀스가 변하지 않다가 입력창 포커스 복원 직후 변했습니다.
- 대기 시간 확대와 메시지 펌핑만으로는 해결되지 않았습니다.
- **Ctrl+C 후 입력창 포커스를 먼저 복원하고 그다음 클립보드를 읽도록 순서를 변경**한 뒤 정상화됐습니다.

이 순서를 원래대로 돌리지 않는 것이 중요합니다. 회귀 테스트는
`test_copy_restores_input_focus_before_waiting_for_clipboard`입니다.
원인을 일반적인 모든 Windows/카카오톡 버전의 동작으로 단정하지 말고, 관측한 재현 조건과 수정 효과로 이해합니다.

## 검증 결과

### 자동 검증

최근 기능 수정 시 `python -m unittest -q test_fishing` **27개 통과**.
히스토리 모든 보기의 Tkinter 생성·갱신 스모크 테스트도 통과했습니다.
카운트다운 1.5초 표시와 창 전환 일시정지 시 카운트다운 숨김은 별도 모의 상태 검사로 확인했습니다.

사용자가 제공한 실제 복사 샘플은 테스트에 포함했습니다.
사용자별 분리, 여러 줄 결과/어종 카드 결합, 반복 복사 중복 방지를 검사합니다.
샘플에 대화 참여자 이름이 포함되므로 외부 공유가 필요하면 익명화 여부를 검토합니다.

### 실제 카카오톡 검증

사용자가 직접 테스트를 허용한 상태에서 수행했습니다. 당시 친구도 같은 방에서 낚시 중이었습니다.

- 사용자 오늘 횟수: **1,004 → 1,005 → 1,006 / 3,000** 갱신 확인
- 기록: **심청이 2,008G / 107EXP**, **가시복 27G / 4EXP**, **옐로우퍼치 45G / 4EXP**
- 합계: **3마리, 2,080G, 115EXP**
- 화면과 JSON 저장을 모두 확인했고 친구의 낚시는 해당 세션 기록에 포함되지 않았습니다.
- 검증 후 매크로를 정지했습니다. 이것은 당시 상태이며 현재 실행 상태를 의미하지 않습니다.

### 아직 실제 동작으로 검증하지 않은 범위

- 자정까지 실제 기다려 예약 재시작하는 전체 흐름
- 실제 미끼 보유량 조회 및 소비, 보정 어종 연속 출현
- 실제 PC 전원 종료 (모의 테스트만 수행)
- 레이드·진주·도감·자동어의 모든 실서비스 메시지 변형

단위 테스트 통과를 위 기능들의 실서비스 검증 완료로 표현하지 않습니다.

## 실행 파일 인계

현재 배포용 경로는 프로젝트 루트의 `FishingMacro.exe`입니다.
카운트다운을 포함한 최신 빌드로 교체했고 `FishingMacro_updated.exe`와 해시 일치를 확인했습니다.

작업 중 파일 잠금 때문에 다음 파일이 함께 남았습니다.

| 파일 | 용도 |
|---|---|
| `FishingMacro.exe` | 사용할 최신 실행 파일 |
| `FishingMacro_updated.exe` | 동일 최신 빌드의 별도 복사본 |
| `dist/FishingMacro.exe` | PyInstaller 빌드 산출물 |
| `FishingMacro_previous_20261027_232923.exe` | 잠긴 이전 파일을 이름 변경해 남긴 백업 |

프로세스 종료 후에도 덮어쓰기 잠금이 남아 기존 EXE를 백업 이름으로 이동하고 새 EXE를 배치했습니다.
앞으로 교체할 때는 실행 여부를 다시 확인하고, 잠금을 이유로 사용자 프로세스를 임의 강제 종료하지 않습니다.
빌드 산출물과 가상환경은 `.gitignore` 대상입니다.

## 현재 제한과 후속 작업 시 유의점

- 기록은 매크로가 실행 중 읽은 범위에 한정되며 과거 JSON 불러오기 UI는 없습니다.
- 명령/답장 순서가 어긋나면 오인식 가능성이 남습니다. 사용자 수용 사항이므로 임의로 큰 재설계하지 않습니다.
- 답장이 없을 때도 반복 카운트가 증가하므로 성공 마릿수와 다를 수 있습니다.
- 클립보드 이미지/파일 보존이나 사용자의 동시 복사와 충돌 방지는 추가하지 않았습니다.
- 자동어 순번은 횟수가 없으면 추정합니다. 오래된 한도/카운트·메시지 누락 상황에서 정확하지 않을 수 있습니다.
- 기존 자동어 해제 실패 대기의 복구 경로 문제는 최초 분석에서 발견했지만 이번 범위에서 수정하지 않았습니다.
- 수동 횟수 0이 허용되면서 첫 반복 뒤 종료 판정하는 기존 동작도 유지됩니다.
- 기록 시각은 관측 시각입니다. 자정 경계에서 지연된 답장은 실제 낚시 날짜와 다를 수 있습니다.
- 미끼 사용은 전송 후 재개하며 실제 소비 성공을 별도 검증하지 않습니다.
- 빌드 도구 버전 고정과 CI는 추가하지 않았습니다.

문서 작성 전 확인한 Git 상태에는 `fishing_macro.py` 수정과 새 모듈·테스트·README가
미커밋으로 남아 있었습니다. 이 작업에서 커밋·푸시·릴리스 업로드는 수행하지 않았습니다.

## 다음 작업 시작 순서

1. 사용자 최신 지시, Git 변경사항, 실제 실행 파일/프로세스 상태를 확인합니다.
2. `docs/`와 본 문서에서 유지할 전제와 검증 한계를 읽습니다.
3. 관련 테스트를 실행하고 실제 입력이 필요한지 판단합니다.
4. 복사 문제는 진단 로그를 먼저 확인하고 개인정보가 포함된 전체 대화를 무작정 출력하지 않습니다.
5. 수정 후 필요한 테스트 및 빌드를 완료하고 루트 EXE의 버전도 맞춥니다.
